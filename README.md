# SPfRAG

A config-driven RAG (Retrieval-Augmented Generation) system for querying industrial product datasheets in natural language. Built with LangChain, evaluated with RAGAS.

## Problem

Industrial datasheets are distributed across dozens of PDF files. Looking up a specific spec (e.g., rated power, MTBF, operating temperature) requires manually opening and searching multiple documents. This system lets users ask questions directly and retrieves answers from the source documents.

## Architecture

```
PDF datasheets → Markdown conversion
    ↓
utility/_representation_.py  — chunking strategy experiments
    ↓
ChromaDB (local vector store)
    ↓
utility/_evaluation_.py      — retrieval + generation + RAGAS scoring
    ↓
application.py               — Gradio demo UI
```

## Tech Stack

| Component | Choice |
|---|---|
| Framework | LangChain |
| Vector DB | ChromaDB (local) |
| Embedding | `BAAI/bge-m3` |
| LLM | `qwen2.5:3b` via Ollama (local) |
| Evaluation | RAGAS |
| UI | Gradio |

## Key Engineering Decisions

**1. Two-stage chunking (db2 / db3)**

`MarkdownHeaderTextSplitter` splits on semantic boundaries (`##`, `###`) to avoid mixing content from different sections. A second pass with `RecursiveCharacterTextSplitter` enforces a hard size limit to prevent GPU OOM during inference.

**2. Model name prefix in chunks**

Multiple datasheets share nearly identical boilerplate text (description, compliance statements), causing embedding vectors to cluster together regardless of model number. Prepending the model name to each chunk (`HS-5102-12A1: <content>`) separates them in embedding space.

**3. Metadata filter**

The LLM extracts the product model number from the question. Retrieval is then filtered to only chunks belonging to that model (`$eq` on source metadata), eliminating cross-model interference entirely.

## Experiment Design

Three chunking strategies × four chunk sizes (300 / 500 / 800 / 1000) = 12 configs total.

| DB | Strategy |
|---|---|
| db1 | `RecursiveCharacterTextSplitter` only |
| db2 | `MarkdownHeaderTextSplitter` (`##`) + Recursive |
| db3 | `MarkdownHeaderTextSplitter` (`##` / `###`) + Recursive |

Evaluation: 20 QA pairs generated by Claude, covering `single_value`, `comparison`, and `enumeration` question types. Judge model: `llama3.2:3b`.

## Evaluation Results

| Config | Faithfulness | Answer Relevancy | Context Precision | Context Recall |
|---|---|---|---|---|
| db1 chunk=300  | 0.640 | 0.712 | 0.854 | **1.000** |
| db1 chunk=500  | 0.612 | 0.826 | 0.746 | 0.933 |
| db1 chunk=800  | 0.602 | 0.757 | 0.704 | 0.795 |
| db1 chunk=1000 | 0.564 | **0.867** | 0.758 | 0.883 |
| db2 chunk=300  | 0.674 | 0.811 | 0.637 | 0.938 |
| db2 chunk=500  | 0.632 | 0.784 | 0.654 | 0.933 |
| db2 chunk=800  | 0.500 | 0.762 | 0.679 | 0.880 |
| db2 chunk=1000 | 0.467 | 0.826 | 0.646 | 0.850 |
| db3 chunk=300  | **0.795** | 0.747 | 0.767 | 0.938 |
| db3 chunk=500  | 0.617 | 0.791 | 0.742 | 0.950 |
| db3 chunk=800  | 0.642 | 0.811 | **0.846** | 0.950 |
| db3 chunk=1000 | 0.542 | 0.773 | 0.833 | 0.975 |

**Selected config: db3 chunk=800**

Highest answer_relevancy and context_precision with no significant weaknesses across all four metrics. Semantic chunking with larger chunks keeps table content intact, which is critical for spec lookup tasks.

**Key observations:**

- db1 chunk=300 achieves perfect context_recall but lowest faithfulness — fixed-size splitting cuts tables mid-row, leaving incomplete context that forces the model to hallucinate
- db3 chunk=300 achieves highest faithfulness — tighter semantic boundaries produce cleaner, more self-contained chunks
- db2 consistently underperforms db3, confirming that `###`-level splitting provides meaningful additional structure for this dataset

## Setup

**Requirements:** Python 3.12, Ollama with `qwen2.5:3b` and `llama3.2` pulled locally.

```bash
conda env create -f environment.yaml
conda activate SimpleRAG
```

**Run evaluation pipeline:**
```bash
# 1. Build vector databases
python generate-vector-database.py

# 2. Run inference
python infer-question-summary.py

# 3. Compute RAGAS scores
python compute-summary-score.py
```

**Launch demo UI:**
```bash
python application.py
```

## Known Limitations

- Judge model (`llama3.2:3b`) has limited instruction-following capability; faithfulness scores may not be fully reliable
- QA test set is LLM-generated and may have uneven difficulty distribution
- Metadata filter currently uses exact match — multi-model datasheets require separate handling
